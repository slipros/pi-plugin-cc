# RESEARCH: tok/s пресета go-developer у разных провайдеров одной модели

> Статус: final (вердикт скептика — refuted, вывод не зафиксирован)
> Дата: 2026-08-11 · Железо: WSL2, 31 ГБ RAM, провайдеры сетевые · Автор прогона: сессия Claude Code

## Вопрос и критерий победы

Модель deepseek-v4-flash доступна через три провайдера. Модель считаем одной и той
же — сравнивается доставка, а не веса: сколько токенов в секунду отдаёт каждый
провайдер под пресетом `go-developer`.

- Первичная метрика: **tok/s по модельному времени** (сгенерированные токены,
  делённые на время прогона за вычетом времени инструментов).
- Вторичные: доля дошедших до конца прогонов, длительность p50, стоимость.
- Порог значимости: разница медиан **> 25%** И непересекающиеся диапазоны
  повторных прогонов. Меньше — считаем шумом сети, победителя не объявляем.

## Кандидаты

| Кандидат | Модель | Провайдер | Источник |
|----------|--------|-----------|----------|
| ollama-pro | `deepseek-v4-flash:0731` | ollama-pro (шлюз) | текущий дефолт пресета |
| openrouter | `deepseek/deepseek-v4-flash-0731` | openrouter | каталог pi |
| opencode-go | `deepseek-v4-flash` | opencode-go | каталог pi |

Пресет `go-developer` во всём остальном одинаков: тот же системный промпт,
песочница, thinking. Меняется только `--model`.

## Методология

- Данные: два задания в `/mnt/d/sandbox/UDMP-3762/lk-api`, все прогоны read-only.
  - **G2 (генерация)** — `--no-tools`, задание на 30 пунктов с фиксированной
    структурой. Инструментов нет вовсе, поэтому модельное время равно всему
    прогону, и tok/s меряется без примеси работы gopls. Основной измеритель.
- Holdout: **задание H** — другой генеративный промпт того же объёма. Не
  запускается до skeptic-гейта.
- Повторов на кандидата: **4**.

- Условия: прогоны **строго последовательные** (параллельные делили бы канал и
  хост), один и тот же репозиторий, одинаковый timeout, одинаковая песочница.
  Порядок кандидатов чередуется между повторами, чтобы разогрев сети и кэш
  gopls не достались одному.
- Бюджет: скачиваний нет, диск 739 ГБ свободно; ~27 прогонов по 20–60 с.

### Поправка методологии после пилота

Первый заход (задание на 12 пунктов, 3 повтора) в результат **не включён**:
объём ответов разошёлся втрое между кандидатами (557 против 4227 токенов), а на
коротком ответе tok/s определяется временем до первого токена, а не скоростью
генерации. Задание заменено на заведомо длинное с жёсткой структурой, повторов
стало 4. Пилот при этом дал полезное наблюдение, которое проверяется отдельно:
**openrouter отвалился в 1 прогоне из 3** (`Upstream error from Ambient`) и ещё
в одном завис без результата.

### Команды

```bash
node ~/.claude/skills/pi/scripts/pi-companion.mjs delegate \
  --preset go-developer --model <кандидат> --no-tools --timeout 300 \
  --background --cwd /mnt/d/sandbox/UDMP-3762/lk-api "<задание>"
```

Метрики берутся из журнала `~/.local/share/pi-plugin/jobs.db`:
`output + reasoning` против `model_ms`.

## Skeptic-гейт

- Вердикт: **refuted**. Вопрос о ранжировании — inconclusive.
- Проверка на holdout: выполнена скептиком, порядок кандидатов перевернулся.

Что было опровергнуто:

1. **Набор G2 недействителен: прогоны шли параллельно, а не последовательно.**
   Все 12 стартовали в окне 23 секунды. Причина — гонка в рецепте ожидания:
   `delegate --background` печатает job-id **до** записи джоба в журнал, поэтому
   немедленный `watch --follow` джоба не находит и выходит за доли секунды.
   Воспроизведено отдельно: `watch --follow` вернулся за 0.44 с на «job pending».
   Под конкуренцией `model_ms` меряет длину очереди: TTFT удалённых провайдеров
   доходил до 68 с против 1.2 с у локального.
2. **Дисперсия больше измеряемой разницы.** Медиана ollama-pro по трём батчам:
   127.1 → 187.6 → 185.3, размах 46% при пороге значимости 25%. Порог в этом
   дизайне недостижим в принципе.
3. **Выброс 11.5 tok/s у openrouter воспроизвёлся** (13.5 в holdout, те же ~214 с
   модельного времени в двух разных батчах, стрим при этом непрерывен). Это
   устойчивый режим деградации провайдера, исключать его из выборки нельзя.
4. **tok/s — функция длины ответа**: внутри кандидатов r = 0.35…0.75. Фиксированные
   накладные амортизируются длинными ответами, поэтому многословный кандидат
   получает более высокий балл.
5. **Метрика отвечает не на тот вопрос.** На одинаковом артефакте (35 пунктов,
   8–10 тыс. знаков) расход токенов различался впятеро. opencode-go лидирует по
   tok/s и при этом втрое медленнее ollama-pro по знакам доставленного ответа.
6. **Допущение «модель одна и та же» не обосновано**: при одинаковом `thinking: max`
   число thinking-дельт 136 / 994 / 1502, различаются max output (16.4K / 65.5K /
   384K), кеширование префикса и нарезка стрима.
7. **Учёт отказов ненадёжен.** opencode-go получал `failed` при полном ответе на
   35 пунктов — причина `Stream ended without finish_reason`. Проверено: у таких
   прогонов в журнале ненулевые `output`/`reasoning` (6139–7743 и 3379–4599), то
   есть статус занижает успешность, хотя токены записаны.
8. **Числитель занижен у ollama-pro**: провайдер не сообщает `reasoning` в usage
   (в журнале 0 при 31 завершённом прогоне), хотя thinking-события в потоке есть.
   Токены генерируются и попадают во время, но не в счёт.

## Вывод

**Сравнение не состоялось.** Ни различие, ни паритет между провайдерами по tok/s
не подтверждены — данные этого не вытягивают, а сама метрика для вопроса выбора
провайдера непригодна.

Единственная воспроизводимая находка: **openrouter периодически уходит в режим
деградации** — 214 с модельного времени в двух независимых батчах (11.5 и 13.5
tok/s) и отказы в 2 прогонах из 7 в первом заходе.

Чтобы вопрос стал разрешимым, нужно: чинить ожидание завершения прогона (опрос
журнала вместо `watch`), мерить по чистому окну генерации вместо `model_ms`,
нормировать на доставленный артефакт, а не на токены, жёстко ограничивать длину
ответа через max output, и брать не меньше 10 повторов без фоновой нагрузки.
