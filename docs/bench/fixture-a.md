# Задача: устойчивая пагинация списка датамартов (B-26)

Репозиторий `data-marketplace`, ветка `feature/UDMP-3766`, BASE `0439916`. Гейты: `make build`, `make lint`, `make test`. Твой deliverable — прод-код и тесты одним коммитом.

## Зачем

Список датамартов сортируется по `updatedAt desc` **без уникального хвоста** — `pkg/datalab/dal/repository/build/showcase_omd.go:72-73`. Датамарты создаются и обновляются пачками, поэтому равные `updatedAt` — обычное дело, а не экзотика. При равных значениях ключа сортировки порядок между запросами страниц не определён: часть записей выдаётся на двух страницах подряд, часть не выдаётся никогда. Классический дефект пагинации, который **не ловится ни гейтами, ни обычными тестами** — только тестом на склейку страниц.

Потребители списка — справочник датамартов в личном кабинете и батч названий, то есть пользователь видит дубли и пропуски прямо в интерфейсе.

## Что сделать

1. Добавить в сортировку **уникальный хвост** — вторичный ключ, гарантирующий полный порядок при равных `updatedAt`. Идентификатор датамарта подходит; выбери то, что реально уникально в этом индексе, и обоснуй выбор в отчёте.
2. Написать **тест на склейку страниц**: набор, где у нескольких записей `updatedAt` совпадает, читается постранично, страницы объединяются — в объединении обязаны быть все записи ровно по одному разу. Тест должен падать на текущей сортировке и проходить после правки.
3. Проверить, нет ли в том же слое других списочных запросов с той же болезнью (сортировка по неуникальному ключу + пагинация). Найдёшь — почини тем же способом; не найдёшь — напиши об этом в отчёте.
