# Git из песочницы: fetch есть, push нет

Устройство git-прокси: как объявляются форджи, откуда берётся токен, что происходит с
редиректами и почему это надёжнее read-only токена. Агенту из этого нужен один факт —
push из песочницы невозможен, — и он записан в скилле.

В образе нет `ssh` — и он там не нужен. Форджи доступны через **git-прокси прогона**: контейнер ходит по http на `host.docker.internal`, настоящий токен подставляется на хосте, а из двух маршрутов smart-HTTP проксируется только fetch. Push отбивается прокси до того, как к запросу прикладывается хоть какой-то креденшл:

```
remote: Push is disabled for this sandbox: the git proxy forwards fetch only.
fatal: unable to access '…': The requested URL returned error: 403
```

Форджи объявляются один раз в корне конфига:

```json
"gitProxy": {
  "gitlab.gid.team": {
    "user": "oauth2",
    "tokenCommand": "phase secrets export GID_TEAM_GITLAB_RO_TOKEN --app personal --env Production --format kv"
  },
  "git.k8s.nomilk.space": {
    "user": "SLI",
    "tokenCommand": "phase secrets export NOMILK_SPACE_FORGEJO_RO_TOKEN --app personal --env Production --format kv",
    "sshPorts": [2222]
  }
}
```

- Токен берётся из `token` (литерал), `tokenEnv` или `tokenCommand` — команда выполняется на хосте, её stderr не логируется (секрет-менеджеры любят цитировать запрос в ошибке). Вывод нормализуется для любого источника: берётся последняя непустая строка (баннер секрет-менеджера перед значением отбрасывается), с неё снимаются `KEY=` и кавычки, `\r` срезается — поэтому `--format kv` у Phase подходит как есть. Значение с управляющим символом внутри отвергается (хост выбывает с предупреждением), а не уходит в заголовок, где раньше роняло процесс. `--app`/`--env` указывать обязательно: без них phase ищет привязку `.phase.json` в каталоге прогона.
- `user` — это логин в basic-аутентификации форджа: у Forgejo/Gitea имя аккаунта, у GitLab PAT — `oauth2`, у GitLab deploy token — выданное ему имя вида `gitlab+deploy-token-42`.
- Контейнеру подкладывается свой `~/.gitconfig`, где все формы адреса — `https://`, `git@host:`, `ssh://…`, `ssh://…:2222/` — переписаны на прокси через credential helper (токен в helper, не в URL — иначе он светился бы в `git remote -v` и в транскрипте). Агенту не нужно знать о прокси: он клонирует по тому URL, который нашёл в remote или в `go.mod`. Хостовый `~/.gitconfig` при этом **не** монтируется: его собственные `insteadOf` переписывают адреса обратно на ssh, которого в образе нет.
- Identity коммитов от этого не зависит — она приходит через `GIT_AUTHOR_*`/`GIT_COMMITTER_*` (см. «От чьего лица коммитит агент»).
- Профиль или пресет сужает список — ключ `gitProxy` лежит **внутри** объекта `sandbox`: `"sandbox": {"profile": "go", "gitProxy": ["git.k8s.nomilk.space"]}` — только этот фордж, `"gitProxy": false` — никакого git по сети. Верхнеуровневый `gitProxy` в пресете игнорируется (он описывает креды хоста, это дело пользовательского конфига).
- Push включается точечно и осознанно: `"allowPush": true` у конкретного хоста.
- Прокси живёт ровно столько, сколько прогон, и закрывается на **любом** выходе (таймаут, отмена, исключение) через `try/finally`; при закрытии обрываются и живые исходящие fetch, чтобы поток с настоящим токеном не пережил прогон. Утёкший run-токен после этого не открывает ничего, а пока прогон жив — открывает только fetch тех репозиториев, которые агент и так читает.

**Почему это надёжнее read-only токена.** Токен зависит от того, что позволяет выпустить фордж (корпоративный GitLab может не разрешить deploy token), а запрет здесь — свойство канала: один и тот же прокси одинаково отбивает `git-receive-pack` на любом хосте. Дополнительно режется всё, что не является smart-HTTP fetch: dumb-HTTP, `..` в пути (в т.ч. `%2e%2e` — сегменты декодируются до проверки), обращения к незаявленным хостам. Попытки push и запросы с чужим run-токеном считаются и выводятся строкой в шапку прогона.

Редирект форджа прокси проходит **сам** (до 3 хопов, гейт на каждом), а не отдаёт клиенту — иначе git при переходе на «новое место» пере-аутентифицируется и ловит challenge посреди согласования (`fatal: expected flush after ref listing`). Это нужно для `go`: он пробует URL без суффикса `.git`, GitLab отвечает 301 на канонический. Канонизация запоминается на прогон, поэтому второй запрос smart-HTTP (POST на тот же путь) сразу идёт на правильный. Редиректом протащить `git-receive-pack` нельзя; редирект на хост вне списка — 502.

**Про адрес прокси.** Слушает на `127.0.0.1`: контейнер приходит через `host.docker.internal`, и на Docker Desktop этот путь выходит на хостовый loopback (замерено — соединения видны как `127.0.0.1 → 127.0.0.1`). Слушатель с настоящими креденшлами на всех интерфейсах не нужен; переопределяется `PI_PROXY_BIND`. Обработчик запроса обёрнут в try/catch: битый запрос из контейнера (например `%zz` в пути) отвечает 400, а не роняет процесс-хост.

Единственная тонкость — гонка: форвардер замечает свежий слушающий сокет с задержкой (замерено между ~320 и ~580 мс: запрос через ~320 мс после `listen` ещё не соединяется, через ~580 мс проходит). Поэтому прогон один раз выжидает `PI_PROXY_SETTLE_MS` (по умолчанию 1000; `=0` отключает) до старта контейнера, вместо того чтобы уронить первый же запрос к модели или fetch.
