# Агенты pi из Claude Code

Все команды — через companion-скрипт в каталоге этого скилла:

```bash
node "<skill-dir>/scripts/pi-companion.mjs" <команда> [флаги] [текст]
```

`<skill-dir>` — базовый каталог скилла, указанный в начале сообщения о его запуске. Дальше в примерах он опускается ради краткости.

| Команда | Назначение |
| --- | --- |
| `delegate [флаги] <задача>` | Отдать задачу агенту pi |
| `review [флаги] [фокус]` | Read-only ревью рабочего дерева или ветки |
| `watch [job-id] [--follow] [--tail N]` | Транскрипт работы агента |
| `steer [job-id] [--follow-up] <текст>` | Отправить указание работающему агенту |
| `status [job-id] [--all] [--global] [--running]` | Список задач и их состояние; `--global` — по всем воркспейсам машины |
| `result [job-id] [--diff]` | Итог завершённой задачи; `--diff` — патч того, что она изменила |
| `wait [job-id...] [--all] [--for N]` | Дождаться завершения фоновых задач |
| `cancel [job-id] [--all [--global]]` | Остановить задачу или все сразу |
| `runs [id] [--all] [--prune]` | Журнал прогонов: что запускали, о чём просили, во что обошлось |
| `rerun <id> [флаги]` | Повторить записанный прогон — теми же настройками или на другой модели |
| `models [поиск] [--stats]` | Каталог моделей, пресеты, системные промты; `--stats` добавляет замеры по факту прогонов |
| `stats [--by …] [--days N]` | Расход и поведение прогонов: токены, tok/s, успешность, p50/p90 — по дням, моделям, пресетам, проектам |
| `sandbox [status\|build\|clean]` | Образ песочницы и её контейнеры |
| `setup` | Проверка установки pi и конфигурации |

## Правила работы

1. **Не делай работу за pi.** Вывод команды возвращай пользователю как есть, без пересказа. Не исправляй то, что нашло ревью, и не доделывай задачу за агента, пока пользователь об этом не попросил.
2. **Долгие задачи — в фон.** `delegate --background` + `Bash(run_in_background: true)`. Форграунд оправдан только для узкого вопроса. Сомневаешься — спроси один раз через `AskUserQuestion` («Run in background» / «Wait for results»).

   `--background` **отсоединяет прогон**: команда проверяет пресет и песочницу, отдаёт работу отдельному процессу и завершается за пару секунд, напечатав job-id. Дальше агент живёт сам — Bash-задача уже закрыта, держать её нечем и убивать нечего. Ошибки конфигурации (неизвестный пресет, несобранный образ) при этом всё равно видны сразу: отсоединение происходит после проверок.

   Текст задачи переезжает вместе с прогоном, поэтому `--stdin` работает и в фоне: `cat brief.md | delegate --background --stdin "Задача 11"` доносит бриф целиком.
3. **Пресет — основной способ запуска.** Если под задачу есть пресет — бери его. Иначе выбирай промт осознанно: `explorer` для исследования, `fixer` для правки кода, `reviewer`/`adversarial` для критики. Если правки не нужны — `--read-only`.
4. **Модель**: если пользователь назвал — используй её. Если нет — не выдумывай, оставь дефолт и укажи в ответе, какая модель отработала.
5. **После write-прогона** посмотри секцию Changes в отчёте — она уже перечисляет коммиты и файлы прогона, отдельно помечая то, что было изменено до его старта. Патч — `result <job> --diff`, ревью именно этих изменений — `review --job <job>`. Коммиты не делай.
6. Если pi упал — сообщи job-id, ошибку и что в логе. Не переписывай задачу молча.
7. **Никогда не оборачивай запуск в `timeout`** и не убивай Bash-задачу руками. Свой лимит у прогона уже есть (`timeoutMs` пресета, по умолчанию 30 мин) — он снимает и pi, и контейнер. Внешний `timeout` бьёт по companion, и в форграунде это оставляет джоб в состоянии `orphaned`: «процесс исчез, результата нет». Остановить осознанно — `cancel`.
8. **Не изобретай ожидание.** Получил job-id — дальше `watch` (смотреть, что происходит) или `wait` (дождаться конца): ни `sleep`, ни самодельных циклов опроса, ни повторного запуска той же задачи. Фоновые ожидания, завершающиеся мгновенно с exit 0, — признак именно этой ошибки; сам прогон в этот момент жив и идёт. У `wait` есть свой дедлайн (`--for`, по умолчанию час), после которого он возвращает управление и ненулевой код.
9. **Наблюдай из того каталога, откуда запускал.** Состояние задач привязано к workspace (бакет по абсолютному пути), поэтому `status`/`watch`/`result`, вызванные из другого места, честно покажут пусто — процесс при этом жив. Работать агенту нужно в другом каталоге — **не переходи туда, а передай `--cwd`**: джоб останется в твоём бакете и не потеряется.

**Бюджет прогона.** Кроме `timeoutMs` есть потолки по расходу: `--max-cost <usd>`, `--max-tokens <n>`, `--max-turns <n>` (и `budget` в пресете). Считаются по usage, который прогон и так сообщает, проверяются после каждого ответа модели; на rpc-движке прогон получает `abort` и успевает сохранить сделанное. Потолок срабатывает **после** превышения, а не предсказывает его: размер сообщения известен, только когда оно оплачено.

## Выбор модели

```bash
delegate --model opencode-go/kimi-k3 --thinking high  "почини падающий тест авторизации"
delegate --provider anthropic --model claude-sonnet-5 "переделай логику ретраев"
delegate --preset fast "прогони линтер и объясни ошибки"   # весь профиль одним флагом
```

- `--model` принимает `provider/id`, короткое имя и подстроку, совпадающую ровно с одной записью каталога (`kimi` → `opencode-go/kimi-k3`). Имя, которое не нашлось или совпало с несколькими, даёт предупреждение, но всё равно уходит в pi. Glob-шаблоны (`anthropic/*`) не поддерживаются.
- `--thinking off|minimal|low|medium|high|xhigh|max`.
- `--preset <имя>` — готовый профиль агента из `.claude/pi/config.json`: модель, thinking, системный промт, инструменты, расширения.
- `models [поиск]` показывает каталог с контекстом и поддержкой thinking.

## Системный промт агента

Один флаг `--system-prompt` принимает три вида значений:

```bash
delegate --system-prompt explorer                "как устроено возобновление сессий?"
delegate --system-prompt @.claude/pi/prompts/dba.md "разбери план запроса"
delegate --system-prompt "Отвечай одним предложением" "что делает этот модуль?"
```

- **Имя** сохранённого промта — ищется в `.claude/pi/prompts/<имя>.md` проекта, затем `~/.claude/pi/prompts/<имя>.md`, затем встроенные в плагине. Встроенные: `reviewer`, `adversarial`, `fixer`, `explorer`; одноимённый файл в проекте их перекрывает.
- **`@путь`** или путь с расширением — файл.
- **Всё остальное** — текст промта как есть.

Если промт не задан, берётся `.claude/pi/SYSTEM.md` проекта, а если и его нет — собственный промт pi. `--append-system-prompt` (можно повторять) и `.claude/pi/APPEND_SYSTEM.md` дополняют промт, а не заменяют.

## Инструменты агента

Встроенные инструменты pi: `read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`. По умолчанию `delegate` разрешает всё, `review` — только чтение.

```bash
delegate --read-only "разберись, почему падает сборка"     # read, grep, find, ls + навигация LSP
delegate --tools read,grep,find,ls,bash "воспроизведи баг, ничего не меняя"
delegate --exclude-tools bash "поправь типы, команды не запускай"
delegate --no-tools "просто подумай вслух над архитектурой"
delegate --write "поправь и закоммить"                       # перекрывает read-only пресета
cat brief.md | delegate --stdin "реализуй задачу по брифу"   # stdin дописывается к промпту
```

`--read-only` и `--write` — старший слой: они перекрывают и пресет, и дефолты команды. Поэтому `review --write` снимает режим только чтения, хотя ревью настроено read-only.

`--read-only` сохраняет и навигацию LSP — `lsp_definition`, `lsp_references`, `lsp_hover`, `lsp_document_symbols`, `lsp_workspace_symbols`, `lsp_more`: поиск вызовов символа ничего не меняет и нужен ревью в первую очередь. `lsp_diagnostics` в набор не входит — вердикт о сломанности кода за гейтами. Учти: `--tools` — белый список, поэтому явно заданный набор отсекает всё неназванное, включая LSP.

Новые инструменты дают расширения pi — включая MCP-серверы через `pi-mcp-adapter`, который читает `.mcp.json` проекта:

```bash
delegate --extension npm:pi-mcp-adapter "сходи в БД через MCP и посчитай строки"
delegate --extension ./tools/my-ext.ts --skill ./skills/db "…"
delegate --no-extensions "чистый прогон без сторонних инструментов"
```

У самого pi **песочницы нет**: `bash`, `edit`, `write` работают с правами пользователя. Давай их только когда задача действительно требует изменений — либо изолируй прогон целиком (ниже).

## Песочница

`--sandbox docker` запускает весь процесс pi в контейнере: инструменты, `!`-команды и расширения исполняются там, с хоста примонтирован только рабочий каталог.

```bash
sandbox build                       # собрать образ (один раз; версия pi = хостовой)
delegate --sandbox docker "перепиши модуль и прогони тесты"
sandbox                             # состояние образа и оставшиеся контейнеры
sandbox clean                       # убрать контейнеры, оставшиеся после падения
```

- Рабочий каталог примонтирован read-write в `/workspace`, правки видны на хосте; всё остальное — домашний каталог, ключи, соседние репозитории — контейнеру недоступно.
- Каждый прогон в песочнице идёт с `PI_OFFLINE=1`, `PI_SKIP_VERSION_CHECK=1` и `PI_TELEMETRY=0` — это дефолт песочницы, а не свойство профиля, поэтому дублировать в профилях не нужно. Контейнеру незачем ходить за обновлениями и слать телеметрию: его единственная законная исходящая связь — модель. Побочно это убирает сетевые проверки со старта каждого прогона.
- Сессии разложены по рабочим каталогам (`PI_CODING_AGENT_SESSION_DIR`): pi бакетит их по cwd, а cwd в контейнере всегда `/workspace`, поэтому раньше в одном бакете лежали транскрипты всех репозиториев сразу и `--session last` мог подцепить чужую сессию.
- **Воркспейс вне `trustedProjects` не делит кэши ни с кем.** Named volume'ы, которые профиль монтирует на запись (кэш модулей, кэш сборки, индекс gopls), заменяются анонимными — они умирают вместе с контейнером, — а каталог агента становится отдельным томом на воркспейс. Причина одна: тома переживают прогон и общие для всех, поэтому отравленный модуль или объект сборки из чужого репозитория подхватил бы следующий прогон в другом репозитории. Цена — холодный кэш сборки; модули всё равно резолвятся мгновенно из хостового download-кэша (`GOPROXY=file://`, read-only). Список доверенных матчится по префиксу: `"trustedProjects": ["~/github"]` покрывает всё внутри. Грубый вариант — `"trustProjectConfig": true`: доверять любому воркспейсу где угодно, то есть вернуть поведение, которое было до появления этой границы.
- Каталог агента — отдельный docker-volume, поэтому хостовые настройки, сессии и установленные пакеты pi внутрь не попадают. Read-only подкладываются два файла: `auth.json` и `models.json` (описания кастомных провайдеров — без него пресет с моделью своего шлюза упал бы с `Unknown provider`).
- **Реальные ключи в контейнер не попадают.** На время прогона поднимается локальный прокси, агенту выдаётся одноразовый токен, а настоящий ключ подставляется уже на хосте. В логе прогона это видно строкой «Credentials stay on the host». Песочница защищает хост от агента, но не защищала бы ключи: у агента внутри есть bash и сеть, и `auth.json` он прочитал бы целиком. Токен живёт ровно столько, сколько прогон: прокси умирает вместе с ним, и утёкший токен уже ничего не открывает.

  **Агент не знает, какая модель ему отвечает.** В контейнере провайдер называется `sandbox`, модель — `agent-model`, настоящее имя подставляет прокси в теле запроса. Отсюда практическая польза: агент не может пересесть на модель подороже у того же провайдера — счёт приходит хозяину аккаунта, а не в песочницу. Поведенческие поля (`api`, `compat`, размер окна) переносятся из настоящей записи: соврать в них значило бы изменить работу pi, а не спрятать имя. В журнал и отчёты пишется реальная модель — статистика остаётся про то, что действительно отвечало.

  Работает и для своих провайдеров из `~/.pi/agent/models.json`, и для встроенных в pi: их адреса берутся из каталога моделей рядом с бинарём `pi` (`MODELS[провайдер][модель].baseUrl`), а описание провайдера подкладывается в контейнерный `models.json`. Если адрес не нашёлся — монтируется запись одного провайдера вместо файла со всеми ключами. Отключается на профиль: `"proxyCredentials": false`.
- **Токены форджей в контейнер тоже не попадают — и push оттуда невозможен.** Тем же приёмом поднимается git-прокси: контейнер получает run-токен и адрес прокси, настоящий токен подставляется на хосте. В шапке прогона строка «Git stays on the host: fetch from … goes through a run-scoped proxy, push is refused». Подробности — «Git из песочницы» ниже.
- Расширения с хостовыми путями внутри контейнера не существуют — companion предупредит. `npm:`/`git:`-источники ставятся внутри и работают.
- Сессии живут в volume: `--session last` между песочными прогонами работает, но хостовую сессию в песочнице продолжить нельзя (и наоборот).

Профиль песочницы целиком настраивается в пресете (`sandbox: { mode, image, network, agentDir, env, mounts, args, memory, cpus, pidsLimit, maxConcurrent, gitProxy }`); `--sandbox none` разово отключает песочницу пресета.

`maxConcurrent` — сколько контейнеров этого профиля разрешено одновременно. Прогон сверх лимита **ждёт свободный слот**, а не падает: провайдер, ограничивший число параллельных сессий, иначе обрывает лишние прогоны на середине. В логе такого прогона видно `Waiting for a free slot: profile <имя> is at its limit of N`; ожидание ограничено таймаутом прогона. Считается по живым контейнерам docker, а не по записям журнала.

**Общий пул на несколько профилей** — когда лимит принадлежит не профилю, а провайдеру за ним. Профиль объявляет `concurrencyGroup`, лимит задаётся один раз в корне конфига:

```json
"concurrencyPools": { "ollama-pro": 3 },
"sandboxProfiles": {
  "go":     { "image": "pi-sandbox-go:latest", "concurrencyGroup": "ollama-pro" },
  "go-mem": { "profile": "go" }
}
```

Теперь `go` и `go-mem` делят одни три слота, а не по три на каждый. Лимит живёт у пула, поэтому профили не могут разойтись во мнении, сколько сессий разрешает провайдер; ссылка на несуществующий пул — ошибка до старта, а не молчаливое «без лимита». Всё это **опционально**: нет `concurrencyGroup` — работает `maxConcurrent` самого профиля, нет и его — лимитов нет вовсе.

При запуске в шапке видно занятость: `Slots: 2/3 in use · pool ollama-pro`, а если слотов не осталось — `— this run waits for a free slot`.

Контейнеры называются `pi-<профиль>-<job-id>` (`pi-go-delegate-msonq…`), поэтому в `docker ps` сразу видно, какой профиль занимает слот.

`memory`, `cpus`, `pidsLimit` — необязательные потолки ресурсов: не заданы — docker ничего не ограничивает, как и было раньше. Смысл появляется на параллельных прогонах: один gopls на большом репозитории держит несколько сотен мегабайт, поэтому три worktree-агента разом — это гигабайты на хосте. Профиль передаёт лимиты наследникам; всё, что этими тремя полями не покрыто, по-прежнему задаётся через `args`.

### Оснастка агента: sandboxProfiles

Образ намеренно голый — node, git, ripgrep. Если агенту нужен тулчейн (собрать Go, прогнать линтер, соблюсти твои гейты на коммит), эта оснастка описывается один раз в `sandboxProfiles` и подключается по имени:

```json
{
  "sandboxProfiles": {
    "go": {
      "mounts": [
        "/home/linuxbrew/.linuxbrew/opt/go/libexec:/usr/local/go:ro",
        "~/go/bin:/gobin:ro",
        "~/.pi/agent/extensions:/pi-agent/host-extensions:ro",
        "pi-plugin-gomod:/home/pi/go/pkg/mod",
        "pi-plugin-gocache:/home/pi/.cache"
      ],
      "env": ["PATH=/usr/local/go/bin:/gobin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"],
      "extensions": ["/pi-agent/host-extensions/custom-gcl-precommit.ts"]
    }
  },
  "presets": {
    "go-fix": { "model": "opencode-go/kimi-k3", "systemPrompt": "fixer", "sandbox": "go" }
  }
}
```

- `extensions`/`skills` профиля подключаются **только** когда песочница активна, поэтому могут ссылаться на контейнерные пути. Гейты живут здесь: гейт, которого нет внутри контейнера, не падает с ошибкой — он просто перестаёт гейтить.
- **LSP.** Расширение `pi-lsp-adapter` вшито в образ (`/usr/local/lib/node_modules/pi-lsp-adapter/src/index.ts`) — ничего не качается на старте. Сам сервер монтируется с хоста (`gopls` статический, работает как есть). Адаптер берёт пути от **домашнего каталога**, а не от `PI_CODING_AGENT_DIR`: конфиг — `$HOME/.pi/agent/lsp.json`, lock — `$HOME/.pi/agent/lsp/lsp.lock.json`. Без записи в lock сервер считается неустановленным даже при `installMode: off` и абсолютном `bin`, а `/lsp install` интерактивен и в headless не отрабатывает — поэтому lock монтируется готовым, с контейнерным путём (`"resolvedCommand": ["/gobin/gopls"]`). Volume под это не нужен: рабочие каталоги адаптера (`pids`, `logs`, `cache`, `workspaces`) создаёт образ, за прогон они остаются пустыми, а дорогой индекс держит сам сервер в `$HOME/.cache` — том, что уже смонтирован.
- Бинари не копируются, а монтируются: `~/go/bin:/gobin:ro` показывает контейнеру тот же файл на диске. Статические бинари (всё, что собрано Go) работают как есть.
- `env` принимает обе формы: `"NAME"` пробрасывает значение с хоста, `"NAME=значение"` задаёт своё. Смонтированный бинарь бесполезен, пока его каталог не в `PATH`.
- Volume-ы (`pi-plugin-gomod:/home/pi/go/pkg/mod`) держат кэши между прогонами — без них каждый прогон пересобирает всё заново.
- `"sandbox": {"profile": "go", "network": "none"}` — взять профиль за основу и переопределить отдельные поля. `--sandbox go` подключает профиль разово. Оснастка (`mounts`, `env`, `extensions`, `skills`, `args`) при этом **добавляется** к профилю, а не заменяет его: `{"profile": "go", "env": ["PI_HOOKS=…"]}` сохраняет профильный `PATH`, без которого ни один смонтированный бинарь не найдётся.
- Профиль сам может ссылаться на `profile` — `go-mem` это `go` плюс CLI памяти, а не его копия. Цикл ссылок сообщается ошибкой, а не подвисает.

Если образ не собран или демон недоступен, прогон падает **до** создания задачи — с текстом, что именно делать.

### Несколько образов

Профиль может назвать свой образ и свой Dockerfile — под каждый стек свой:

```json
"sandboxProfiles": {
  "go":   { "image": "pi-plugin-sandbox:latest" },
  "node": { "image": "pi-sandbox-node:latest", "dockerfile": "node" }
}
```

```bash
sandbox                 # таблица образов: собран/нет, из какого файла, какие профили используют
sandbox build node      # собрать один (можно назвать и профиль, и имя образа)
sandbox build --all     # собрать все, что знает конфиг
```

Dockerfile ищется как `<имя>.Dockerfile` в `<проект>/.claude/pi/sandbox/`, затем `~/.claude/pi/sandbox/`, затем в самом плагине — как и промты. **Держи свои образы в `~/.claude/pi/sandbox/`**: плагин обновляется из git, и правка его файла потеряется при следующем обновлении, а одноимённый пользовательский файл перекрывает плагинный и переживает апдейт.

Базовый образ (`base.Dockerfile`) — фундамент: в нём pi, git, ripgrep, make, LSP-адаптер. Стековые образы наследуются от него:

```dockerfile
FROM pi-plugin-sandbox:latest
USER root
RUN apt-get update && apt-get install -y --no-install-recommends gcc libc6-dev && rm -rf /var/lib/apt/lists/*
```

Что куда класть:

- **в образ** — то, у чего есть версия и что должно быть воспроизводимым: SDK языка, `gopls`, компилятор C. Без `gcc` не работает `go test -race` (детектор гонок линкуется через cgo), а это часть тестового гейта, поэтому `CGO_ENABLED=1` там же прописан явно — чтобы случайный `CGO_ENABLED=0` в окружении не выключил его молча;
- **монтировать с хоста** — локально собранные инструменты, которых нет ни в одном реестре: `custom-gcl` (golangci-lint с правилами gid.team), `mockery`, `protoc-gen-*`, `tea`. Они живут в `~/go/bin` и монтируются профилем;
- **кеш модулей — file-прокси, не копия.** Хостовый `~/go/pkg/mod/cache/download` монтируется read-only, `GOPROXY=file:///host-gomod,https://proxy.golang.org,direct`. Всё уже скачанное (включая приватные `gitlab.gid.team`) доступно мгновенно, контейнер в хостовый кеш не пишет, распаковка идёт в свой volume. Проверено прогоном с `--network none`: `go mod download` и `go test -race -count=1` проходят без сети.

### Git из песочницы: fetch есть, push нет

В образе нет `ssh` — и он там не нужен. Форджи доступны через **git-прокси прогона**: контейнер ходит по http на `host.docker.internal`, настоящий токен подставляется на хосте, а из двух маршрутов smart-HTTP проксируется только fetch. Push отбивается прокси до того, как к запросу прикладывается хоть какой-то креденшл:

```
remote: Push is disabled for this sandbox: the git proxy forwards fetch only.
fatal: unable to access '…': The requested URL returned error: 403
```

Форджи объявляются один раз в корне конфига:

```json
"gitProxy": {
  "gitlab.gid.team": {
    "user": "oauth2",
    "tokenCommand": "phase secrets export GID_TEAM_GITLAB_RO_TOKEN --app personal --env Production --format kv"
  },
  "git.k8s.nomilk.space": {
    "user": "SLI",
    "tokenCommand": "phase secrets export NOMILK_SPACE_FORGEJO_RO_TOKEN --app personal --env Production --format kv",
    "sshPorts": [2222]
  }
}
```

- Токен берётся из `token` (литерал), `tokenEnv` или `tokenCommand` — команда выполняется на хосте, её stderr не логируется (секрет-менеджеры любят цитировать запрос в ошибке). Вывод нормализуется для любого источника: берётся последняя непустая строка (баннер секрет-менеджера перед значением отбрасывается), с неё снимаются `KEY=` и кавычки, `\r` срезается — поэтому `--format kv` у Phase подходит как есть. Значение с управляющим символом внутри отвергается (хост выбывает с предупреждением), а не уходит в заголовок, где раньше роняло процесс. `--app`/`--env` указывать обязательно: без них phase ищет привязку `.phase.json` в каталоге прогона.
- `user` — это логин в basic-аутентификации форджа: у Forgejo/Gitea имя аккаунта, у GitLab PAT — `oauth2`, у GitLab deploy token — выданное ему имя вида `gitlab+deploy-token-42`.
- Контейнеру подкладывается свой `~/.gitconfig`, где все формы адреса — `https://`, `git@host:`, `ssh://…`, `ssh://…:2222/` — переписаны на прокси через credential helper (токен в helper, не в URL — иначе он светился бы в `git remote -v` и в транскрипте). Агенту не нужно знать о прокси: он клонирует по тому URL, который нашёл в remote или в `go.mod`. Хостовый `~/.gitconfig` при этом **не** монтируется: его собственные `insteadOf` переписывают адреса обратно на ssh, которого в образе нет.
- Identity коммитов от этого не зависит — она приходит через `GIT_AUTHOR_*`/`GIT_COMMITTER_*` (см. «От чьего лица коммитит агент»).
- Профиль или пресет сужает список — ключ `gitProxy` лежит **внутри** объекта `sandbox`: `"sandbox": {"profile": "go", "gitProxy": ["git.k8s.nomilk.space"]}` — только этот фордж, `"gitProxy": false` — никакого git по сети. Верхнеуровневый `gitProxy` в пресете игнорируется (он описывает креды хоста, это дело пользовательского конфига).
- Push включается точечно и осознанно: `"allowPush": true` у конкретного хоста.
- Прокси живёт ровно столько, сколько прогон, и закрывается на **любом** выходе (таймаут, отмена, исключение) через `try/finally`; при закрытии обрываются и живые исходящие fetch, чтобы поток с настоящим токеном не пережил прогон. Утёкший run-токен после этого не открывает ничего, а пока прогон жив — открывает только fetch тех репозиториев, которые агент и так читает.

**Почему это надёжнее read-only токена.** Токен зависит от того, что позволяет выпустить фордж (корпоративный GitLab может не разрешить deploy token), а запрет здесь — свойство канала: один и тот же прокси одинаково отбивает `git-receive-pack` на любом хосте. Дополнительно режется всё, что не является smart-HTTP fetch: dumb-HTTP, `..` в пути (в т.ч. `%2e%2e` — сегменты декодируются до проверки), обращения к незаявленным хостам. Попытки push и запросы с чужим run-токеном считаются и выводятся строкой в шапку прогона.

Редирект форджа прокси проходит **сам** (до 3 хопов, гейт на каждом), а не отдаёт клиенту — иначе git при переходе на «новое место» пере-аутентифицируется и ловит challenge посреди согласования (`fatal: expected flush after ref listing`). Это нужно для `go`: он пробует URL без суффикса `.git`, GitLab отвечает 301 на канонический. Канонизация запоминается на прогон, поэтому второй запрос smart-HTTP (POST на тот же путь) сразу идёт на правильный. Редиректом протащить `git-receive-pack` нельзя; редирект на хост вне списка — 502.

**Про адрес прокси.** Слушает на `127.0.0.1`: контейнер приходит через `host.docker.internal`, и на Docker Desktop этот путь выходит на хостовый loopback (замерено — соединения видны как `127.0.0.1 → 127.0.0.1`). Слушатель с настоящими креденшлами на всех интерфейсах не нужен; переопределяется `PI_PROXY_BIND`. Обработчик запроса обёрнут в try/catch: битый запрос из контейнера (например `%zz` в пути) отвечает 400, а не роняет процесс-хост.

Единственная тонкость — гонка: форвардер замечает свежий слушающий сокет с задержкой (замерено между ~320 и ~580 мс: запрос через ~320 мс после `listen` ещё не соединяется, через ~580 мс проходит). Поэтому прогон один раз выжидает `PI_PROXY_SETTLE_MS` (по умолчанию 1000; `=0` отключает) до старта контейнера, вместо того чтобы уронить первый же запрос к модели или fetch.

### Контейнеры внутри песочницы: профиль go-dind

Тесты на `testcontainers-go` поднимают БД контейнером — в обычном профиле такого нет и быть не должно. Профиль `go-dind` даёт прогону **свой** rootless-демон: его контейнеры живут внутри песочницы, умирают вместе с ней и в `docker ps` на хосте не видны.

```bash
delegate --sandbox go-dind "почини интеграционные тесты advertising-api"
sandbox build go-dind      # образ собирается отдельно от go
```

Ни хостового сокета, ни `--privileged`. Всё, что понадобилось (замерено, не взято из инструкции):

| Что | Зачем |
|---|---|
| `--security-opt seccomp=@sandbox/dind-seccomp.json` | дефолтный профиль docker блокирует `unshare`/`mount`/`clone` с `CLONE_NEW*` — без них rootless не стартует. `@sandbox/` резолвится по тем же каталогам, что и Dockerfile (проект → `~/.claude/pi/sandbox` → плагин), чтобы не хардкодить абсолютный путь |
| `--device /dev/net/tun` | RootlessKit создаёт tap-интерфейс; без него падает на `ip tuntap add` |
| `DOCKERD_ROOTLESS_ROOTLESSKIT_FLAGS=--pidns` | со своим PID namespace демон получает собственный `/proc` и может писать sysctl в свои сетевые namespace |
| volume `pi-dind-images` под `~/.local/share/docker` | иначе образы качаются заново каждый прогон |
| `TESTCONTAINERS_HOST_OVERRIDE=127.0.0.1` | иначе testcontainers адресует контейнеры через `172.17.0.1` и виснет на проверке готовности |
| `TESTCONTAINERS_RYUK_DISABLED=true` | уборщик не нужен: всё внутри умирает вместе с песочницей |

`docker compose` в образе есть (plugin) — для E2E против compose-стека репозитория, не только testcontainers. `DOCKER_HOST`/`XDG_RUNTIME_DIR` не задаются в env профиля: entrypoint выводит их из `id -u`, чтобы образ работал под любым uid.

**Не понадобились:** `apparmor=unconfined` (на Docker Desktop AppArmor не активен; на нативном Linux с активным AppArmor профиль `docker-default` доложит часть mount-операций поверх seccomp — там, скорее всего, понадобится), `systempaths=unconfined` (`/proc/kcore` и `/proc/sysrq-trigger` остаются замаскированными), `--device /dev/fuse` (overlay2 работает поверх volume нативно), `--privileged`.

**Профиль seccomp** генерируется из профиля rootless podman (`containers/common`) скриптом `make-dind-seccomp.py` рядом с Dockerfile — там же зафиксированы URL upstream, дата, sha256 исходника и результата, и команда воспроизведения (`--fetch` скачивает и сверяет хэш). Он разрешает четыре сисколла, которые upstream держит за `CAP_SYS_ADMIN`: `sethostname`, `setdomainname`, `setns`, `chroot`. Их выполняет вложенный runc, а docker сверяет capability-гейт с правами **внешнего** контейнера, где этой capability нет. Разрешение сисколла не даёт привилегии: ядро по-прежнему требует `CAP_SYS_ADMIN` в том namespace, которым владеет вызывающий — он есть у вложенного рантайма и отсутствует у процесса, который полез бы к хосту. (Cap-гейтованный ALLOW вместо безусловного здесь **не** работает — проверено, ломает вложенный демон по той же причине: гейт резолвится по caps внешнего контейнера.)

**Версия docker в образе закреплена на 28.x** (проверка в Dockerfile валит сборку, если пришло другое). В 29.x скрипт запуска пишет `net.ipv4.ip_forward` через sysctl и падает на read-only `/proc/sys`; лечится это только `systempaths=unconfined`, то есть возвратом доступа к `/proc/kcore` ради одного sysctl.

**Переносимость.** Образ собирается под uid хоста (`RUNTIME_UID`/`RUNTIME_GID` companion передаёт из `process.getuid()`): для uid ≠ 1000 заводится пользователь и subuid-диапазон, иначе RootlessKit не стартует. При смене пользователя образ нужно пересобрать (`sandbox build go-dind`).

**Параллельные go-dind прогоны.** Хранилище образов у каждого прогона своё — монтирование помечено `:isolate`, и docker выдаёт контейнеру анонимный volume, умирающий вместе с ним. Иначе два демона дерутся за эксклюзивный lock containerd на общем volume и портят `meta.db`; общего RW-хранилища образов для нескольких dind в docker нет ([moby#40196](https://github.com/moby/moby/issues/40196)), поэтому изоляция — единственный способ поднять пул `dind` выше единицы. Кеши модулей и сборки при этом остаются общими: `:isolate` действует на одно монтирование, в отличие от `isolateCaches`, который анонимизирует все.

Цена изоляции — холодное хранилище образов на каждом старте, и её снимает **зеркало-кеш на хосте**:

```bash
docker run -d --restart=always --name pi-registry-mirror -p 5000:5000 \
  -v pi-registry-cache:/var/lib/registry \
  -e REGISTRY_PROXY_REMOTEURL=https://registry-1.docker.io registry:2
```

Профиль передаёт демону внутри песочницы `PI_REGISTRY_MIRROR` (по умолчанию `http://host.docker.internal:5000`), entrypoint пишет из него `registry-mirrors` + `insecure-registries` + `max-concurrent-downloads: 10` в `daemon.json` до старта dockerd. Первый прогон греет зеркало, остальные тянут слои по локальной сети. Зеркало недоступно — docker сам идёт в апстрим, прогон не ломается. Проксируется только Docker Hub: приватные реестры ходят напрямую.

**Остаточный риск.** Проверено pen-test-агентом изнутри: побег на хост **не достигнут**. seccomp реально отдаёт EPERM на `fsopen`/`open_by_handle_at`/`bpf`/`userfaultfd`/`kexec` даже с полными caps в user namespace — это и есть примитивы userns-escape. Агент может создавать user namespace и монтировать внутри него, но `mount_setattr` на host-маунтах даёт EPERM (их владелец — init userns), а побег остаётся только через уязвимость ядра, не через штатный механизм. Хостового демона, устройств хоста, немаскированного `/proc` и `CAP_SYS_ADMIN` снаружи у него нет. Прогон, ослабляющий изоляцию, сам об этом сообщает: `Sandbox replaces the default seccomp profile…`, `Sandbox passes the host device /dev/net/tun…`.

### Другой каталог: --cwd

Агент может работать не там, где ты стоишь:

```bash
delegate --preset go-developer --cwd ~/proj/bookmarks "реализуй SPEC.md"
review --cwd ../other-repo                              # ревью чужого диффа
```

`--cwd` двигает **только рабочий каталог агента**: он монтируется в `/workspace`, в нём же pi запускается и по нему `review` считает дифф. Записи о задачах остаются там, откуда ты запускал, — поэтому `status`, `watch`, `steer` и `result` работают из твоего каталога, без перехода в чужой репозиторий. В шапке прогона и в `status` появляется строка `Working directory`, а если каталог вне твоего workspace — предупреждение: правки лягут туда, а не сюда.

Каталог должен существовать: опечатка даёт ошибку до создания задачи, а не агента, запущенного не в том дереве. Путь резолвится от текущего каталога (`../other-repo`, `~/proj/x` — оба годятся) и подтягивается до корня git-репозитория, если он внутри.

Конфиг, пресеты и промты при этом берутся **из твоего** каталога, а не из целевого: `--cwd` даёт агенту код, а не чужие настройки. Нужен `SYSTEM.md` целевого репозитория — подключи явно: `--append-system-prompt @../other-repo/.claude/pi/SYSTEM.md`.

### Разовая папка: --mount

Профилю не нужно знать про всё заранее. `--mount host:container[:ro]` добавляет каталог к тому профилю, с которым идёт прогон:

```bash
delegate --preset go-fix --mount ~/proj/shared-lib:/shared:ro "перенеси модуль на новое API"
delegate --preset go-fix --mount ./fixtures:/fixtures:ro --mount ~/dumps:/dumps:ro "почини парсер"
```

- Повторяемый; относительный путь хоста резолвится от рабочего каталога (иначе docker принял бы `./fixtures` за имя volume и смонтировал пустоту).
- Монтирование на путь, который профиль уже занял, **заменяет** его, а не добавляет второй.
- Без песочницы `--mount` — ошибка, а не молчаливый no-op: монтировать некуда, pi и так видит всю файловую систему.

**Git-worktree рабочим каталогом — работает, монтировать руками ничего не надо.** У worktree нет своего репозитория: `.git` — файл с абсолютным путём общего. Companion распознаёт это по `--cwd` и сам монтирует общий `.git` тем же путём, каким его называет файл; в шапке прогона появляется строка `Worktree: shared … mounted`. Отсюда параллелизм внутри одного репозитория: несколько worktree — несколько фоновых прогонов, каждый в своей ветке. Монтирование обязано быть на запись (git держит там index и HEAD ветки), поэтому заменять его своим `--mount … :ro` нельзя — сломается уже `git add`.

## Наблюдение за работой агента

```bash
watch                       # транскрипт последней (или текущей) задачи
watch --tail 20             # только хвост
watch <job-id> --since 149  # только то, что произошло после прошлой проверки
watch <job-id> --follow --for 30  # живой поток 30 секунд, потом возврат
watch <job-id> --follow     # живой поток, пока задача не завершится
```

Транскрипт показывает ходы, вызовы инструментов с аргументами и результатами, очередь указаний и ответы агента с расходом токенов.

Каждый снапшот заканчивается курсором — это и есть способ вести фоновую задачу изнутри хода Claude Code: заглянул с `--since <курсор>`, получил только новое, при необходимости отправил `steer`, заглянул снова. Голый `--follow` не вернётся, пока агент работает: в чате используй его только с `--for <секунд>`, иначе предложи пользователю запустить у себя в терминале через `!`.

`status` даёт короткую сводку по всем задачам, `result` — итоговый ответ. Расход токенов виден в обоих: строка `Usage: in … · out … · $…` обновляется **по ходу прогона** (на каждом ответе модели), поэтому у работающего агента можно спросить, сколько он уже сжёг, не читая транскрипт.

**По умолчанию все они смотрят состояние того workspace, в котором вызваны** — джобы разложены по бакетам, ключ бакета это абсолютный путь рабочего каталога. Запустил из `~/proj/foo` — `status` из `~/proj/bar` покажет пусто, хотя агент жив и контейнер работает. Весь флот сразу — `status --global` (и `cancel --all --global`, чтобы остановить всё); фильтры `--running`, `--status`, `--preset`, `--model` сужают список.

**Дождаться конца, не опрашивая статус.** `wait` блокируется, пока задачи не завершатся, и возвращает ненулевой код, если истёк дедлайн или прогон закончился не успехом:

```bash
wait                    # последняя живая задача
wait <job> <job>        # именно эти
wait --all --for 600    # все идущие, максимум 10 минут
```

Уведомление вместо ожидания — хук `onFinish` в своём конфиге или `--notify '<команда>'` на прогон: команда выполняется на хосте по завершении (в том числе неуспешном), в окружении есть `PI_JOB_ID`, `PI_JOB_STATUS`, `PI_JOB_TITLE`, `PI_JOB_SUMMARY`, `PI_JOB_ELAPSED`, `PI_JOB_LOG`. Из конфига репозитория такой хук вырезается: это исполнение кода на хосте, а `.claude/pi/config.json` агент в песочнице может дописать себе сам.

## От чьего лица коммитит агент

```json
"defaults": { "git": { "name": "pi agent", "email": "pi@nomilk.space" } },
"presets": { "go-developer": { "git": { "email": "go-developer@nomilk.space" } } }
```

```bash
delegate --git-name "pi agent" --git-email pi@nomilk.space "..."
```

Задаёт `GIT_AUTHOR_*` и `GIT_COMMITTER_*` — git читает их раньше любого конфига, поэтому одна настройка покрывает и песочницу (где `~/.gitconfig` может вовсе отсутствовать), и хостовой прогон (где он есть, но называет человека, а не агента). В шапке прогона видно строкой `Commits as: …`.

Имя и адрес задаются только парой: половина identity — ошибка до старта, git с ней всё равно откажется коммитить. Слои сливаются по полям, поэтому глобально можно задать имя, а в пресете — только адрес.

**Приоритет: флаги → твой gitconfig → пресет.** Блок `git` в пресете или `defaults` — это *фолбэк* на случай, когда git сам не знает identity; настроенную для этого дерева личность он не перекрывает. Нужен коммит от лица агента там, где identity настроена, — передавай флаги на прогон.

**Флагов нет — identity берётся из рабочего каталога.** Companion спрашивает её у git в том каталоге, где будет работать агент, и передаёт внутрь. Поэтому правила `includeIf "gitdir:…"` из твоего `~/.gitconfig` работают и в песочнице:

```gitconfig
[includeIf "gitdir:/home/sli/sandbox/"]
	path = /home/sli/sandbox/.gitconfig
[includeIf "gitdir:/home/sli/sandbox/umdp/"]
	path = /home/sli/sandbox/umdp/.gitconfig
```

Правила применяются сверху вниз, поэтому более узкое ставится ниже общего. Резолв происходит **на хосте, до старта контейнера** — иначе правило не сработало бы никогда: внутри репозиторий лежит в `/workspace`, а путь, на который правило смотрит, там не существует.

## Учёт токенов и поведение моделей

```bash
stats                       # за 30 дней, по дням
stats --by model            # какая модель как себя вела
stats --by preset --days 7  # за неделю, по пресетам
stats --by workspace --all  # за всё время, по проектам
stats --by status           # чем прогоны заканчивались
stats --by kind             # delegate против review
models --stats <поиск>      # каталог моделей + факты по ним
```

Отчёт даёт не только токены: `ok` — доля прогонов, дошедших до конца; `ctx avg`/`ctx max` — сколько контекстного окна прогон занимал в пике; `tok/s` — скорость модели; `p50`/`p90` — длительность прогона; `tools`/`err` — вызовы инструментов и ошибки в них.

**`ctx` отвечает на вопрос «влезаем ли в окно», а колонка `in` — нет.** Каждый turn переотправляет весь диалог, поэтому сумма `input` кратно больше того, что модель держала одновременно: прогон на 4 turn'а даёт 30K суммарного входа при пике контекста 10K. Считается по максимуму `input + cache + output` одного обмена.

**`tok/s` считается по окну генерации** — от первого контентного фрейма до последнего чанка, суммарно по запросам прогона, замер снимает прокси. Раньше знаменателем было модельное время (прогон минус инструменты), куда попадали prefill, очередь провайдера и сеть: на замеренном прогоне это давало 122 tok/s против реальных 259.

Два исключения. Прогоны **без телеметрии прокси** (записанные раньше или запущенные без песочницы) в метрику не входят вовсе — прочерк вместо подмешивания другого замера. И **ответы короче 1000 выходных токенов**: токены из первого фрейма сгенерированы до открытия окна, и чем короче ответ, тем сильнее это завышает число. Соседняя колонка `out/run` — средняя длина ответа за этой скоростью: бакеты, где длины различаются в разы, несравнимы при любом знаменателе.

Два утверждения, которые тут стояли раньше и оказались неверны при проверке. Токены **не** приходят крупными пачками: замер с обеих сторон канала даёт медианный интервал между дельтами 11 мс. И **не** «89% времени уходит на gopls»: по 68 транскриптам инструменты заняли 35% времени, из них gopls — 3.5%, а bash — 96%, почти половина которого один `go build ./...`. Прежде чем менять модель на более быструю, посмотри на брифы задач, а не на LSP.

Считается по долговременному журналу `~/.local/share/pi-plugin/jobs.db` (SQLite), а не по файлам задач: те лежат рядом с ним — в `~/.local/share/pi-plugin/state/`, разложены по бакетам рабочих каталогов, по 50 последних на бакет. Журнал пишется в двух точках — когда прогон начинается и когда заканчивается.

**Повтор и сравнение прогонов.** Журнал хранит задачу, ответ и настройки, поэтому прогон воспроизводим:

```bash
runs                        # прогоны этого воркспейса
runs --all --days 7         # по всей машине за неделю
runs <id>                   # чем кормили и что ответил
rerun <id>                  # ещё раз, теми же настройками
rerun <id> --model other/m  # та же задача на другой модели
rerun <id> --append "и не трогай миграции"
rerun <id> --prompt "переписанная задача"
runs <id> --json | jq -r .prompt > task.md   # достать текст, поправить руками
rerun <id> --stdin < task.md                 # и отправить обратно
```

`rerun` сохраняет выбранное (пресет, модель, thinking, песочницу, бюджеты), остальное резолвит заново по текущему конфигу. Текст задачи тоже правится: `--append` дописывает указание к исходной задаче (можно несколько раз), `--prompt`/`--stdin` заменяют её целиком, сохраняя настройки. Достать текст руками: `runs <id> --json` — копия из журнала (редактированная, до 32 КБ), `result <job> --json` — исходник целиком, пока жив файл задачи. Замена оживляет и прогон, у которого текст уже истёк: настройки живут дольше промпта. Тексты — это содержимое чужих репозиториев на диске, поэтому они редактируются по шаблонам секретов, режутся по 32 КБ и живут 90 дней (`runs --prune`, плюс автоматическая уборка не чаще раза в сутки); счётчики и стоимость не истекают никогда. Файл журнала и его каталог — 0600/0700.

**Что видит прокси.** Каждый запрос к модели из песочницы проходит через прокси учётных данных — единственную точку на хосте, где обмен виден целиком (pi ретраит HTTP-ошибки внутри себя и переносит лишь шесть ключей usage). На запрос пишется строка: статус, вид ошибки (`transport`, `timeout`, `aborted`, `truncated`), TTFB, время до первого контентного фрейма, окно генерации, самая долгая пауза внутри него, размеры, заголовки лимитов и сырой usage провайдера. Свёртку показывает `runs <id>`. Тела запросов, промты, тексты ответов и заголовки не пишутся никогда.

Стоимость показывается, только если провайдер её отдаёт: у `ollama-pro` и `opencode-go` `cost` приходит нулевым, поэтому честный ответ там — токены, а не деньги.

## Управление на лету

Пока задача выполняется, ей можно отправить указание:

```bash
steer "хватит читать файлы, переходи к правке"
steer <job-id> "сфокусируйся на internal/auth"
steer --follow-up "когда закончишь, добавь тесты"
```

- `steer` доставляется после текущего хода агента, до следующего обращения к модели — это способ развернуть агента, пока он работает.
- `--follow-up` доставляется, когда агент закончит текущую работу.
- Если агент уже отстрелялся, но прогон ещё жив (короткое окно между «agent settled» и выходом процесса), сообщение уходит новым промптом в ту же сессию. Завершённую задачу направить нельзя — `steer` откажется и предложит запустить новый прогон с `--session <id>`.
- Работает только на движке `rpc` (он по умолчанию). У `--engine json` канала управления нет.

`cancel` сначала пробует мягкий `abort` (сессия pi остаётся целой и результат частично сохраняется) и только потом убивает процесс.

## Продолжение сессии

Каждый прогон сохраняет id сессии pi. Продолжить:

```bash
delegate --session last "теперь примени первый вариант"
delegate --session <session-id> "…"
delegate --fresh "…"                 # принудительно новая сессия
```

Пользователь может открыть ту же сессию у себя: `pi --session <session-id>`.

## Конфигурация

Необязательна. `~/.claude/pi/config.json` — личные дефолты, `<repo>/.claude/pi/config.json` — проектные (перебивают личные, флаги перебивают оба).

```json
{
  "defaults": { "model": "openrouter/deepseek/deepseek-v4-flash-0731", "thinking": "high" },
  "presets": {
    "fast":  { "model": "opencode-go/deepseek-v4-flash", "thinking": "off" },
    "audit": { "model": "opencode-go/kimi-k3", "systemPrompt": "adversarial", "readOnly": true },
    "dba":   {
      "model": "opencode-go/kimi-k3",
      "systemPrompt": "@.claude/pi/prompts/dba.md",
      "appendSystemPrompt": ["Отвечай по-русски."],
      "tools": "read,grep,find,ls,bash"
    }
  },
  "commands": { "review": { "preset": "audit" } }
}
```

**Пресет — это целый агент, а не только модель.** В нём можно задать любое поле запуска: `model`, `provider`, `thinking`, `systemPrompt`, `appendSystemPrompt`, `tools`, `excludeTools`, `extensions`, `skills`, `sandbox`, `mounts`, `readOnly`, `noTools`, `noBuiltinTools`, `noExtensions`, `noSkills`, `timeoutMs`, `engine`. Задал один раз — дальше запускаешь `--preset dba`.

Один дефолт задан за тебя: `excludeTools: ["ask_question"]` — прогон неинтерактивный, спрашивать некого, и вопрос агента просто сожжёт ход. Вернуть инструмент: `"excludeTools": []` в любом слое.

Значения разрешаются послойно, сверху вниз: флаги → пресет → дефолты команды → общие дефолты. Исключение — commit-identity: там между флагами и пресетом вклинивается твой gitconfig (см. «От чьего лица коммитит агент»). Системный промт выбирается целиком, поэтому `--system-prompt` в командной строке полностью заменяет пресетный. Списки `appendSystemPrompt`, `extensions`, `skills` и `mounts` со всех слоёв складываются.

### Подкрутить глобальный пресет под проект

Проектный конфиг **сливается** с пользовательским по полям, поэтому в репозитории пишется только отличие:

```json
{
  "presets": {
    "go-review": {
      "model": "opencode-go/kimi-k3",
      "appendSystemPrompt": ["Сервис на sqlc: миграции генерируются, руками не править."]
    }
  },
  "sandboxProfiles": { "go": { "mounts": ["~/proj/protos:/protos:ro"] } }
}
```

Промт, `readOnly`, песочница и весь Go-тулчейн достаются из глобальных определений нетронутыми. Правила слияния:

- **Оснастка складывается** — `appendSystemPrompt`, `extensions`, `skills`, `mounts`, `env`, `args`. Совпавшая запись занимает место унаследованной: mounts сопоставляются по контейнерному пути, env — по имени переменной.
- **Решения заменяются** — `model`, `thinking`, `systemPrompt`, `sandbox`, `readOnly`, `tools`, `excludeTools`, `timeoutMs`.
- **`null` удаляет** — `"sandbox": null` снимает песочницу, заданную глобально. Единственный выход из слияния.

Вложенные объекты сливаются так же: `"sandbox": {"network": "none"}` сохраняет image, mounts и остальное из нижнего слоя.

**Системный промт под проект** — три способа, от разового к постоянному: `--system-prompt @./.claude/pi/prompts/try-a.md` на один прогон; файл `<проект>/.claude/pi/prompts/<имя>.md` затеняет одноимённый глобальный для всех пресетов; `<проект>/.claude/pi/APPEND_SYSTEM.md` дописывается к любому промту всегда.

Если что-то не работает — начни с `setup`: он покажет, найден ли бинарь pi, есть ли доступные модели, какие конфиги подхвачены и где лежит состояние задач.
