# Агенты pi из Claude Code

Все команды — через `pia`:

```bash
pia <команда> [флаги] [текст]
```

Это короткий вход в companion-скрипт — шим `bin/pia` плагина, поставленный симлинком
в `PATH` (обычно `~/.local/bin/pia`); полная форма
`node "<skill-dir>/scripts/pi-companion.mjs" …` работает по-прежнему и нужна
только там, где шима нет в `PATH`. `pia` без аргументов печатает список команд.
Префикс `pia` в примерах ниже обязателен и не сокращается: `wait` — встроенная
команда shell, `watch` — отдельная программа, и без префикса запустится не то.

| Команда | Назначение |
| --- | --- |
| `delegate [флаги] <задача>` | Отдать задачу агенту pi |
| `review [флаги] [фокус]` | Read-only ревью рабочего дерева или ветки |
| `watch [job-id] [--follow] [--tail N]` | Транскрипт работы агента |
| `steer [job-id] [--follow-up] <текст>` | Отправить указание работающему агенту |
| `status [job-id] [--all] [--global] [--running]` | Список задач и их состояние; `--global` — по всем воркспейсам машины |
| `result [job-id] [--diff]` | Итог завершённой задачи; `--diff` — патч того, что она изменила |
| `wait [job-id...] [--all] [--for N]` | Дождаться завершения фоновых задач |
| `events [--follow] [--tail N] [--workspace]` | Поток «прогон закончился» по всему флоту — канал пробуждения (п. 2) |
| `cancel [job-id] [--all [--global]]` | Остановить задачу или все сразу |
| `runs [id] [--all] [--prune]` | Журнал прогонов: что запускали, о чём просили, во что обошлось |
| `rerun <id> [флаги]` | Повторить записанный прогон — теми же настройками или на другой модели |
| `continue [<сессия>\|last] [флаги] <текст>` | Продолжить сессию тем же агентом: пресет, модель и песочница едут следом |
| `sessions [<сессия>] [--all] [--global]` | Что можно продолжить: возраст сессии, состояние кэша, контур, размер контекста |
| `models [поиск] [--stats]` | Каталог моделей: контекст, потолок вывода, thinking, картинки; `--stats` добавляет замеры по факту прогонов |
| `presets` | Настроенные агенты: описание, модель, промт, песочница, теги и вычисленные возможности |
| `stats [--by …] [--days N]` | Расход и поведение прогонов: токены, tok/s, успешность, p50/p90 — по дням, моделям, пресетам, проектам |
| `sandbox [status\|build\|clean]` | Образ песочницы и её контейнеры |
| `setup` | Проверка установки pi и конфигурации |

## Правила работы

1. **Не делай работу за pi.** Вывод команды возвращай пользователю как есть, без пересказа. Не исправляй то, что нашло ревью, и не доделывай задачу за агента, пока пользователь об этом не попросил.
2. **Долгие задачи — в фон, и канал пробуждения ставится ОДИН раз на сессию.** `pia delegate --background` отсоединяет прогон: команда проверяет пресет и образ песочницы, отдаёт работу отдельному процессу и завершается за пару секунд, напечатав job-id. Дальше агент живёт вне harness — держать его нечем и убивать нечего. Ошибки конфигурации (неизвестный пресет, несобранный образ) видны сразу: отсоединение происходит после проверок.

   **Никто внутри harness не знает, что отсоединённый прогон закончился.** `<task-notification>` рождается только из завершения объекта harness — фоновой Bash-задачи, `Monitor`, субагента. Пока такого объекта нет, закрытый ход не проснётся никогда: это не «иногда не сработает», а гарантия. Замерено: волна простояла готовой 25 минут, о завершении сообщил пользователь.

   **Канал — `pia events --follow` в `Monitor`.** Ставится один раз, в начале работы с pi, и дальше покрывает весь флот и все волны:

   ```
   Monitor(command: "pia events --follow", description: "завершения агентов pi", persistent: true)
   ```

   Каждый закончившийся прогон приходит в чат отдельной строкой — id, исход, время, пресет, каталог, заголовок задачи. **Приходят все исходы**, не только успех: `failed`, `cancelled` и `orphaned` (прогон, чей процесс убили — он не успевает сказать о себе ничего, его находит опрос раз в 20 секунд). Поэтому тишина в канале значит «ещё работает», а не «умер молча».

   Почему не ожидание на каждый джоб: `wait` — одноразовый канал. Его надо переармировать после каждой волны, забыл один раз — пробуждения нет; и он молча умирает (замерено: четыре ожидания подряд убиты средой, после чего механизм был брошен и следующая задача простояла 39 минут). Один долгоживущий канал переармировать не нужно, а его смерть видна сразу — `Monitor` сообщает о своём завершении.

   **Ход при живых джобах закрывать можно — но только когда канал поднят.** Нет канала — не закрывай.

   **`wait` остаётся для точечного «дождаться именно этих перед приёмкой»** — когда результат нужен в этом же ходе:

   ```bash
   pia delegate --preset go-developer --background --cwd <repo> "<бриф>"   # обычный Bash, отдаёт job-id
   pia wait --all --for 3600                                              # Bash(run_in_background: true)
   ```

   Тогда будит завершение именно этой `wait`-задачи. **Разбудило — сверься со `status`, прежде чем идти за `result`:** у `wait` свой дедлайн `--for`, и вышел он раньше агента — уведомление придёт ровно такое же, только с ненулевым кодом при живом прогоне. **Не заворачивай `wait` в пайп** (`| tail -3`): код возврата станет кодом `tail`, всегда нулевым, и дедлайн при живых агентах придёт как «завершено успешно». Ожидание в форграунде — только на заведомо короткий прогон: Bash рубит вызов на 10 минутах, а `wait` этого лимита не знает.

   **Перезапуск сессии канал не переживает.** `Monitor` живёт ровно столько, сколько сессия; после `--continue`, `--resume` или падения терминала первым действием подними его заново. Джобы при этом живы — их видно в `pia status --global`, а пропущенные завершения догоняются `pia events --tail 20`.

   Текст задачи переезжает вместе с прогоном, поэтому `--stdin` работает и в фоне: `cat brief.md | pia delegate --background --stdin "Задача 11"` доносит бриф целиком.

3. **Пресет — основной способ запуска.** Если под задачу есть пресет — бери его. Иначе выбирай промт осознанно: `explorer` для исследования, `fixer` для правки кода, `reviewer`/`adversarial` для критики. Если правки не нужны — `--read-only`.
4. **Модель**: если пользователь назвал — используй её. Если нет — не выдумывай, оставь дефолт и укажи в ответе, какая модель отработала.
5. **После write-прогона** посмотри секцию Changes в отчёте — она уже перечисляет коммиты и файлы прогона, отдельно помечая то, что было изменено до его старта. Патч — `pia result <job> --diff`, ревью именно этих изменений — `pia review --job <job>`. Коммиты не делай.
6. Если pi упал — сообщи job-id, ошибку и что в логе. Не переписывай задачу молча.
7. **Никогда не оборачивай запуск в `timeout`** и не убивай Bash-задачу руками. Свой лимит у прогона уже есть (`timeoutMs` пресета, по умолчанию 30 мин) — он снимает и pi, и контейнер. Внешний `timeout` бьёт по companion, и в форграунде это оставляет джоб в состоянии `orphaned`: «процесс исчез, результата нет». Остановить осознанно — `cancel`.
8. **Не изобретай ожидание.** Есть ровно три инструмента: `pia events --follow` (канал на всю сессию), `pia wait` (дождаться названных джобов), `pia watch` (смотреть транскрипт). Ни `sleep`, ни самодельных циклов опроса, ни повторного запуска той же задачи.

   **`until ! pia status <job> | grep -q running` — не ожидание, а гонка.** Пока джоб не перешёл в `running`, `grep` не находит ничего, условие истинно сразу, и цикл выходит через секунды после старта агента — уведомление приходит с ложным «готово» (замерено: 17 секунд на живом прогоне). Системная подсказка harness про `until`-цикл верна для файлов и портов, но не для джобов pi: у них есть свой канал.

   **Фоновая задача, завершившаяся мгновенно с exit 0, ждала не то.** В фон попал `pia delegate --background` (п. 2) или опрос вроде `status`: они и должны выходить сразу. Прогон в этот момент жив, а уведомление о «завершении» относится к команде, а не к агенту — перепроверяй `status`.

9. **Наблюдай из того каталога, откуда запускал.** Состояние задач привязано к workspace (бакет по абсолютному пути), поэтому `status`/`watch`/`result`, вызванные из другого места, честно покажут пусто — процесс при этом жив. Работать агенту нужно в другом каталоге — **не переходи туда, а передай `--cwd`**: джоб останется в твоём бакете и не потеряется.

**Бюджет прогона.** Кроме `timeoutMs` есть потолки по расходу: `--max-cost <usd>`, `--max-tokens <n>`, `--max-turns <n>` (и `budget` в пресете). Считаются по usage, который прогон и так сообщает, проверяются после каждого ответа модели; на rpc-движке прогон получает `abort` и успевает сохранить сделанное. Потолок срабатывает **после** превышения, а не предсказывает его: размер сообщения известен, только когда оно оплачено.

## Выбор модели

```bash
pia delegate --model opencode-go/kimi-k3 --thinking high  "почини падающий тест авторизации"
pia delegate --provider anthropic --model claude-sonnet-5 "переделай логику ретраев"
pia delegate --preset fast "прогони линтер и объясни ошибки"   # весь профиль одним флагом
```

- `--model` принимает `provider/id`, короткое имя и подстроку, совпадающую ровно с одной записью каталога (`kimi` → `opencode-go/kimi-k3`). Имя, которое не нашлось или совпало с несколькими, даёт предупреждение, но всё равно уходит в pi. Glob-шаблоны (`anthropic/*`) не поддерживаются.
- `--thinking off|minimal|low|medium|high|xhigh|max`.
- `--preset <имя>` — готовый профиль агента из `.claude/pi/config.json`: модель, thinking, системный промт, инструменты, расширения.
- `pia models [поиск]` показывает каталог с контекстом и поддержкой thinking.
- **Пометка `vision \`skill\`` в `presets` бьёт колонку `Images` в `models`.** Первая про агента, вторая про модель: агенту смонтирован скилл `vision`, и картинку он посмотрит даже текстовой моделью — просто назови путь к файлу в брифе. Пометка вычисляется из резолва (скилл + `bash`), поэтому снятый монтаж её убирает сам.
- Поле `tags` в пресете — ручная разметка для того, что из конфига не выводится: домен, цена, свои правила. `presets` печатает её рядом с вычисленным.
- `pia presets` показывает настроенных агентов и системные промты. Это разные вопросы: «чем ответить» — `models`, «кому поручить» — `presets`; второй отвечает мгновенно, потому что каталога моделей не касается вовсе.

## Системный промт агента

Один флаг `--system-prompt` принимает три вида значений:

```bash
pia delegate --system-prompt explorer                "как устроено возобновление сессий?"
pia delegate --system-prompt @.claude/pi/prompts/dba.md "разбери план запроса"
pia delegate --system-prompt "Отвечай одним предложением" "что делает этот модуль?"
```

- **Имя** сохранённого промта — ищется в `.claude/pi/prompts/<имя>.md` проекта, затем `~/.claude/pi/prompts/<имя>.md`, затем встроенные в плагине. Встроенные: `reviewer`, `adversarial`, `fixer`, `explorer`; одноимённый файл в проекте их перекрывает.
- **`@путь`** или путь с расширением — файл.
- **Всё остальное** — текст промта как есть.

Если промт не задан, берётся `.claude/pi/SYSTEM.md` проекта, а если и его нет — собственный промт pi. `--append-system-prompt` (можно повторять) и `.claude/pi/APPEND_SYSTEM.md` дополняют промт, а не заменяют.

## Инструменты агента

Встроенные инструменты pi: `read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`. По умолчанию `delegate` разрешает всё, `review` — только чтение.

```bash
pia delegate --read-only "разберись, почему падает сборка"     # read, grep, find, ls + навигация LSP
pia delegate --tools read,grep,find,ls,bash "воспроизведи баг, ничего не меняя"
pia delegate --exclude-tools bash "поправь типы, команды не запускай"
pia delegate --no-tools "просто подумай вслух над архитектурой"
pia delegate --write "поправь и закоммить"                       # перекрывает read-only пресета
cat brief.md | pia delegate --stdin "реализуй задачу по брифу"   # stdin дописывается к промпту
```

`--read-only` и `--write` — старший слой: они перекрывают и пресет, и дефолты команды. Поэтому `pia review --write` снимает режим только чтения, хотя ревью настроено read-only.

`--read-only` сохраняет и навигацию LSP — `lsp_definition`, `lsp_references`, `lsp_hover`, `lsp_document_symbols`, `lsp_workspace_symbols`, `lsp_more`: поиск вызовов символа ничего не меняет и нужен ревью в первую очередь. `lsp_diagnostics` в набор не входит — вердикт о сломанности кода за гейтами. Учти: `--tools` — белый список, поэтому явно заданный набор отсекает всё неназванное, включая LSP.

Новые инструменты дают расширения pi — включая MCP-серверы через `pi-mcp-adapter`, который читает `.mcp.json` проекта:

```bash
pia delegate --extension npm:pi-mcp-adapter "сходи в БД через MCP и посчитай строки"
pia delegate --extension ./tools/my-ext.ts --skill ./skills/db "…"
pia delegate --no-extensions "чистый прогон без сторонних инструментов"
```

У самого pi **песочницы нет**: `bash`, `edit`, `write` работают с правами пользователя. Давай их только когда задача действительно требует изменений — либо изолируй прогон целиком (ниже).

## Песочница

`--sandbox docker` (или имя профиля) уводит в контейнер весь процесс pi: инструменты, `!`-команды и расширения работают внутри, хост недоступен.

```bash
pia sandbox build                       # собрать образ (один раз; версия pi = хостовой)
pia delegate --sandbox docker "перепиши модуль и прогони тесты"
pia sandbox                             # состояние образа и оставшиеся контейнеры
pia sandbox clean                       # убрать контейнеры, оставшиеся после падения
```

Что из этого важно на каждом прогоне:

- рабочий каталог примонтирован read-write в `/workspace/<имя каталога>` — имя сохраняется, чтобы рецепты сборки вида `$(notdir $(CURDIR))` считали внутри то же, что снаружи; правки видны на хосте, остальной файловой системы хоста внутри нет;
- **реальные ключи провайдера в контейнер не попадают** — агент видит провайдера `sandbox` и модель `agent-model`, поэтому на вопрос «какая ты модель» честно не ответит;
- **push из песочницы невозможен**: форджи открыты только на чтение, отказ выглядит как `403` и `Push is disabled for this sandbox`. Коммитить агент может, пушит супервизор;
- расширения, заданные хостовыми путями, внутри не существуют — companion предупреждает на старте;
- у профиля есть потолок одновременных контейнеров: слоты заняты — прогон ждёт, занятость видна в шапке (`Slots: 2/3 in use · pool ollama-pro`).

Профили, образы, пулы и устройство изоляции — `docs/sandbox.md`, git-прокси — `docs/git-proxy.md`.

### Контейнеры внутри песочницы: профиль agent

Тесты на `testcontainers` поднимают БД контейнером — в облегчённом профиле такого нет и быть не должно. Контейнеры даёт профиль `agent`, он же стоит у всех рабочих пресетов:

```bash
pia delegate --preset go-developer "почини интеграционные тесты"   # профиль agent уже в пресете
pia sandbox build agent                                            # образ один на все стеки
```

Внутри — свой rootless-демон (`PI_DIND=1`), без хостового сокета и без `--privileged`; несколько таких прогонов идут параллельно, у каждого своё хранилище образов. Демон поднимается до старта агента, `DOCKER_HOST` уже указывает на его сокет. Профиль без контейнеров — `agent-lite` (на нём работает `explorer`). Как всё устроено, чем оплачена изоляция и что настраивается на хосте — `docs/dind.md`.

### Другой каталог: --cwd

Агент может работать не там, где ты стоишь:

```bash
pia delegate --preset go-developer --cwd ~/proj/bookmarks "реализуй SPEC.md"
pia review --cwd ../other-repo                              # ревью чужого диффа
```

`--cwd` двигает **только рабочий каталог агента**: он монтируется в `/workspace/<имя каталога>`, в нём же pi запускается и по нему `review` считает дифф. Записи о задачах остаются там, откуда ты запускал, — поэтому `status`, `watch`, `steer` и `result` работают из твоего каталога, без перехода в чужой репозиторий. В шапке прогона и в `status` появляется строка `Working directory`, а если каталог вне твоего workspace — предупреждение: правки лягут туда, а не сюда.

Каталог должен существовать: опечатка даёт ошибку до создания задачи, а не агента, запущенного не в том дереве. Путь резолвится от текущего каталога (`../other-repo`, `~/proj/x` — оба годятся) и подтягивается до корня git-репозитория, если он внутри.

Конфиг, пресеты и промты при этом берутся **из твоего** каталога, а не из целевого: `--cwd` даёт агенту код, а не чужие настройки. Нужен `SYSTEM.md` целевого репозитория — подключи явно: `--append-system-prompt @../other-repo/.claude/pi/SYSTEM.md`.

### Разовая папка: --mount

Профилю не нужно знать про всё заранее. `--mount host:container[:ro]` добавляет каталог к тому профилю, с которым идёт прогон:

```bash
pia delegate --preset go-fix --mount ~/proj/shared-lib:/shared:ro "перенеси модуль на новое API"
pia delegate --preset go-fix --mount ./fixtures:/fixtures:ro --mount ~/dumps:/dumps:ro "почини парсер"
```

- Повторяемый; относительный путь хоста резолвится от рабочего каталога (иначе docker принял бы `./fixtures` за имя volume и смонтировал пустоту).
- Монтирование на путь, который профиль уже занял, **заменяет** его, а не добавляет второй.
- Без песочницы `--mount` — ошибка, а не молчаливый no-op: монтировать некуда, pi и так видит всю файловую систему.

**Git-worktree рабочим каталогом — работает, монтировать руками ничего не надо.** У worktree нет своего репозитория: `.git` — файл с абсолютным путём общего. Companion распознаёт это по `--cwd` и сам монтирует общий `.git` тем же путём, каким его называет файл; в шапке прогона появляется строка `Worktree: shared … mounted`. Отсюда параллелизм внутри одного репозитория: несколько worktree — несколько фоновых прогонов, каждый в своей ветке. Монтирование обязано быть на запись (git держит там index и HEAD ветки), поэтому заменять его своим `--mount … :ro` нельзя — сломается уже `git add`.

## Наблюдение за работой агента

```bash
pia watch                       # транскрипт последней (или текущей) задачи
pia watch --tail 20             # только хвост
pia watch <job-id> --since 149  # только то, что произошло после прошлой проверки
pia watch <job-id> --follow --for 30  # живой поток 30 секунд, потом возврат
pia watch <job-id> --follow     # живой поток, пока задача не завершится
```

Транскрипт показывает ходы, вызовы инструментов с аргументами и результатами, очередь указаний и ответы агента с расходом токенов.

Каждый снапшот заканчивается курсором — это и есть способ вести фоновую задачу изнутри хода Claude Code: заглянул с `--since <курсор>`, получил только новое, при необходимости отправил `steer`, заглянул снова. Голый `--follow` не вернётся, пока агент работает: в чате используй его только с `--for <секунд>`, иначе предложи пользователю запустить у себя в терминале через `!`.

`status` даёт короткую сводку по всем задачам, `result` — итоговый ответ. Расход токенов виден в обоих: строка `Usage: in … · out … · $…` обновляется **по ходу прогона** (на каждом ответе модели), поэтому у работающего агента можно спросить, сколько он уже сжёг, не читая транскрипт.

**Обрыв на потолке вывода прогон чинит сам.** Модель, ушедшая в повтор, упирается в
потолок ответа; усечённый вызов инструмента движок отбрасывает, и финальным ответом
становится текстовая половина — фраза-намерение вроде «now let me wire this up».
Поэтому, увидев обрыв на последнем ответе, прогон **сам продолжает сессию** (контекст
цел, задача не начинается заново) — в логе это строка «Ответ обрезан на потолке
вывода — работа не доведена. Продолжаю сессию…».

Причина обрыва распознаётся в любом написании провайдера — `length` (OpenAI),
`max_tokens` (Anthropic), `MAX_TOKENS` (Google), `max_output_tokens`; регистр и
пробелы не важны. Берётся она из самого прогона (агент сообщает, почему кончил
последний ответ), поэтому работает и без песочницы; телеметрия прокси — только
запасной источник, а прокси поднимается лишь в песочнице.

Лимит — на **подряд идущие** обрывы: по умолчанию 10, меняется переменной окружения
`PI_TRUNCATION_RETRIES` (0 — выключить; мусор и отрицательное дают дефолт). Она
читается у companion на хосте: в контейнер не передаётся, поля пресета под неё нет.
Довёл ответ до конца — счётчик обнуляется, и следующий обрыв получает полный лимит:
прогон живёт часами, и обрыв в его начале ничего не говорит о том, застряла ли модель
сейчас. Отдельного потолка на весь прогон нет намеренно — прогон ограничивают его
таймаут и бюджет, и оба считаются **на прогон целиком**, а не заново на каждое
продолжение.

**Ответ отдаётся целиком — на обоих движках.** Куски, разорванные потолком,
склеиваются обратно в один ответ, между ними маркер `[продолжение после обрыва на
потолке вывода]`; кусков может быть сколько угодно, и склейка происходит даже когда
попытки кончились на обрезанном ответе — недоведённая работа читается целиком или не
читается вовсе. Для прогона, чей deliverable сам текст (read-only исследователь,
ревью), написанное до обрыва и есть работа.

Отличается только механика продолжения:

- **rpc (по умолчанию)** — промт продолжения уходит в живой канал той же сессии, pi не
  перезапускается. Попытка засчитывается и печатается только после успешной отправки;
  если pi отклонил продолжение или молча не подхватил его (минута), прогон завершается
  сам, а не стоит до hard-таймаута, и говорит об этом в ошибках.
- **json** — отдельный проход: новый процесс pi с `--session` той же сессии. Нового
  прохода не будет, если прогон остановлен бюджетом или таймаутом, не получил id
  сессии или у него не осталось времени.

Сколько раз companion досылал продолжение за прогон, видно в записи задачи и в отчёте
`result`: «The answer hit the output ceiling N time(s) and the run continued itself».
Считается одинаково на обоих движках; разница лишь в том, что json может восстановиться
только на хвосте прогона (каждая попытка — новый процесс, продолжать середину нечего), а
rpc — в любой момент.

**Прогон, чей последний ответ так и остался обрезанным → `phase: truncated`, строка
джоба идёт с ⚠️ вместо галочки.** Это значит «задача НЕ выполнена», что бы ни говорил
код возврата pi: `result` пишет это словами в секции `## Problems` (она появляется даже
без других ошибок), а `pia wait` возвращает ненулевой код. Принимать результат по
отчёту нельзя, работу нужно смотреть самому. Обрыв в СЕРЕДИНЕ прогона так не
помечается — он стоит токенов и повтора, но работа доходит до конца.

**По умолчанию все они смотрят состояние того workspace, в котором вызваны** — джобы разложены по бакетам, ключ бакета это абсолютный путь рабочего каталога. Запустил из `~/proj/foo` — `status` из `~/proj/bar` покажет пусто, хотя агент жив и контейнер работает. Весь флот сразу — `pia status --global` (и `pia cancel --all --global`, чтобы остановить всё); фильтры `--running`, `--status`, `--preset`, `--model` сужают список.

**Узнать, что прогон закончился.** Каждый прогон, дошедший до терминального состояния, сам пишет строку в машинный журнал событий — без настройки, для всех воркспейсов сразу. `events` его читает:

```bash
pia events                  # последние 20 завершений по всей машине
pia events --tail 5         # короче
pia events --workspace      # только этот бакет
pia events --follow         # поток: строка на каждое следующее завершение
pia events --follow --for 600 --poll 30   # ограничить время и период опроса осиротевших
```

`--follow` — это и есть канал пробуждения из п. 2 правил: он ставится в `Monitor(persistent: true)`, живёт всю сессию и приносит в чат по строке на каждый конец — `completed`, `failed`, `cancelled` и `orphaned` (прогон, чей процесс убили: он не успевает сказать о себе ничего, его ловит опрос). Начинает с конца журнала — прошлые завершения не пересказывает, для догона есть `--tail N`. Строка самодостаточна: id, исход, время, пресет, модель, каталог, заголовок задачи; `phase: truncated` идёт с ⚠️, а не с галочкой.

**Дождаться именно этих джобов, не опрашивая статус.** `wait` блокируется, пока названные задачи не завершатся, и возвращает ненулевой код, если истёк дедлайн, прогон закончился не успехом или остался обрезанным (`phase: truncated`):

```bash
pia wait                    # последняя живая задача
pia wait <job> <job>        # именно эти
pia wait --all --for 600    # все идущие, максимум 10 минут
```

Job-id, только что напечатанный `delegate --background`, `wait` дождётся: запись отсоединённого прогона появляется в журнале не мгновенно, и команда даёт ей до 30 секунд (но не дольше собственного `--for`), а не отвечает «No pi job matches».

**В чате `wait` ставится в `Bash(run_in_background: true)`** — тогда он и ход не держит, и разбудит по завершении (п. 2 правил). В форграунде его дедлайн `--for` конкурирует с лимитом самого Bash: тот рубит вызов на 10 минутах, и волна, идущая полчаса, оборвётся по стороннему таймауту, а не по своему.

Канал наружу, к человеку, — хук `onFinish` в своём конфиге или `--notify '<команда>'` на прогон: команда выполняется на хосте по завершении (в том числе неуспешном), в окружении есть `PI_JOB_ID`, `PI_JOB_STATUS`, `PI_JOB_TITLE`, `PI_JOB_SUMMARY`, `PI_JOB_ELAPSED`, `PI_JOB_LOG`. Годится для десктопного уведомления или мессенджера; **тебя он не будит** — для этого есть `events --follow`. Из конфига репозитория такой хук вырезается: это исполнение кода на хосте, а `.claude/pi/config.json` агент в песочнице может дописать себе сам.

## От чьего лица коммитит агент

```json
"defaults": { "git": { "name": "pi agent", "email": "pi@nomilk.space" } },
"presets": { "go-developer": { "git": { "email": "go-developer@nomilk.space" } } }
```

```bash
pia delegate --git-name "pi agent" --git-email pi@nomilk.space "..."
```

Задаёт `GIT_AUTHOR_*` и `GIT_COMMITTER_*` — git читает их раньше любого конфига, поэтому одна настройка покрывает и песочницу (где `~/.gitconfig` может вовсе отсутствовать), и хостовой прогон (где он есть, но называет человека, а не агента). В шапке прогона видно строкой `Commits as: …`.

Имя и адрес задаются только парой: половина identity — ошибка до старта, git с ней всё равно откажется коммитить. Слои сливаются по полям, поэтому глобально можно задать имя, а в пресете — только адрес.

**Приоритет: флаги → твой gitconfig → пресет.** Блок `git` в пресете или `defaults` — это *фолбэк* на случай, когда git сам не знает identity; настроенную для этого дерева личность он не перекрывает. Нужен коммит от лица агента там, где identity настроена, — передавай флаги на прогон.

**Флагов нет — identity берётся из рабочего каталога.** Companion спрашивает её у git в том каталоге, где будет работать агент, и передаёт внутрь. Поэтому правила `includeIf "gitdir:…"` из твоего `~/.gitconfig` работают и в песочнице:

```gitconfig
[includeIf "gitdir:/home/sli/sandbox/"]
	path = /home/sli/sandbox/.gitconfig
[includeIf "gitdir:/home/sli/sandbox/umdp/"]
	path = /home/sli/sandbox/umdp/.gitconfig
```

Правила применяются сверху вниз, поэтому более узкое ставится ниже общего. Резолв происходит **на хосте, до старта контейнера** — иначе правило не сработало бы никогда: внутри репозиторий лежит под `/workspace/`, а путь, на который правило смотрит, там не существует.

## Учёт токенов и поведение моделей

```bash
pia stats                       # за 30 дней, по дням
pia stats --by model            # какая модель как себя вела
pia stats --by preset --days 7  # за неделю, по пресетам
pia stats --by workspace --all  # за всё время, по проектам
pia stats --by status           # чем прогоны заканчивались
pia stats --by kind             # delegate против review
pia models --stats <поиск>      # каталог моделей + факты по ним
```

`ok` — доля прогонов, дошедших до конца; `ctx avg/max` — пик контекста, а не сумма входа; стоимость показывается, только если провайдер её отдаёт. Как считаются эти цифры и чего в них нет — `docs/telemetry.md`.

Три таблицы отвечают на разные вопросы: первая — сколько работа стоила, вторая — как модель ломалась (рассуждение на ход, пустые ходы, ответы в потолок, серии повторов), третья — сколько кода прогон сдвинул. В третьей: сколько строк прочитано и записано на прогон, сколько снесено правками, отношение «читал:писал» и перечитывания одного файла. Прогон, который пишет больше, чем читает, меняет код, которого не видел. Считается по вызовам инструментов агента (`read`/`write`/`edit`) — чтение через `bash: cat` не считается и не угадывается; колонка «замерено» говорит, на скольких прогонах корзины замер вообще есть.

Та же строка есть в отчёте прогона и в `pia runs <id>` — `File work: read … · wrote … · re-reads …`.


**Повтор и сравнение прогонов.** Журнал хранит задачу, ответ и настройки, поэтому прогон воспроизводим:

```bash
pia runs                        # прогоны этого воркспейса
pia runs --all --days 7         # по всей машине за неделю
pia runs <id>                   # чем кормили и что ответил
pia rerun <id>                  # ещё раз, теми же настройками
pia rerun <id> --model other/m  # та же задача на другой модели
pia rerun <id> --append "и не трогай миграции"
pia rerun <id> --prompt "переписанная задача"
pia runs <id> --json | jq -r .prompt > task.md   # достать текст, поправить руками
pia rerun <id> --stdin < task.md                 # и отправить обратно
```

`rerun` сохраняет выбранное (пресет, модель, thinking, песочницу, бюджеты), остальное резолвит заново по текущему конфигу. Текст задачи тоже правится: `--append` дописывает указание к исходной задаче (можно несколько раз), `--prompt`/`--stdin` заменяют её целиком, сохраняя настройки. Достать текст руками: `pia runs <id> --json` — копия из журнала (редактированная, до 32 КБ), `pia result <job> --json` — исходник целиком, пока жив файл задачи. Замена оживляет и прогон, у которого текст уже истёк: настройки живут дольше промпта. Тексты — это содержимое чужих репозиториев на диске, поэтому они редактируются по шаблонам секретов, режутся по 32 КБ и живут 90 дней (`pia runs --prune`, плюс автоматическая уборка не чаще раза в сутки); счётчики и стоимость не истекают никогда. Файл журнала и его каталог — 0600/0700.

## Управление на лету

Пока задача выполняется, ей можно отправить указание:

```bash
pia steer "хватит читать файлы, переходи к правке"
pia steer <job-id> "сфокусируйся на internal/auth"
pia steer --follow-up "когда закончишь, добавь тесты"
```

- `steer` доставляется после текущего хода агента, до следующего обращения к модели — это способ развернуть агента, пока он работает.
- `--follow-up` доставляется, когда агент закончит текущую работу.
- Если агент уже отстрелялся, но прогон ещё жив (короткое окно между «agent settled» и выходом процесса), сообщение уходит новым промптом в ту же сессию. Завершённую задачу направить нельзя — `steer` откажется и предложит запустить новый прогон с `--session <id>`.
- Работает только на движке `rpc` (он по умолчанию). У `--engine json` канала управления нет.

`cancel` сначала пробует мягкий `abort` (сессия pi остаётся целой и результат частично сохраняется) и только потом убивает процесс.

## Продолжение сессии

Каждый прогон сохраняет id сессии pi. Продолжают её командой `continue`:

```bash
pia continue last "теперь примени первый вариант"
pia continue 01a05965 "допиши тесты"      # хватает префикса id, он же печатается в отчёте
pia continue last --fresh "…"             # тот же агент, история с нуля
pia sessions                              # что тут вообще можно продолжить
```

`continue` наследует контур прогона-родителя: пресет, модель, thinking, песочницу,
рабочий каталог, бюджеты. Флаги перекрывают что угодно из этого. Наследование —
не удобство: **сэндбоксная сессия лежит в volume песочницы, и продолжение без неё
её не видит вовсе** (`No session found matching <uuid>`). По той же причине
подсказка «открой у себя» верна только для несэндбоксных прогонов — их сессия
лежит на хосте, в `~/.pi/agent/sessions/<ключ-каталога>/`.

**Кэш дороже сессии.** Файл сессии не протухает никогда, а вот кэш промпта у
провайдера — да, и продолжение переигрывает провайдеру ВСЮ историю: внутри окна
кэша это почти бесплатно, за его пределами те же токены оплачиваются заново по
полной входной ставке. Поэтому у продолжения есть гейт: сессия старше TTL
отклоняется (exit 1) с указанием возраста, TTL, провайдера и размера контекста.
Пройти его — `--stale-ok` (плачу за переигрывание осознанно) или `--fresh`
(агент тот же, история сброшена). TTL настраивается, по умолчанию 40 минут:

```json
"cacheTtl": { "default": "40m", "providers": { "anthropic": "5m" } }
```

`delegate --session <id>` тоже работает и проходит тот же гейт, но **ничего не
наследует** — ни пресета, ни песочницы; в отчёте об этом предупреждение. Для
продолжения работы бери `continue`.

Сессии бакетируются по каталогу, из которого запускали. Из другого каталога
`last` не найдётся («No previous pi session recorded for this workspace»), а
явный id упрётся в вопрос pi «Session found in different project? Fork? [y/N]»,
который в неинтерактивном прогоне отвечает сам себе «нет» и отдаёт пустой
результат. Лечится `--cwd` или запуском оттуда же; найти нужный каталог —
`pia sessions --global`.

## Конфигурация

Необязательна. `~/.claude/pi/config.json` — личные дефолты, `<repo>/.claude/pi/config.json` — надстройка проекта; проектный слой действует, только если владелец его доверил. Значения разрешаются послойно: флаги → пресет → дефолты команды → `defaults`.

**Пресет — это целый агент, а не только модель:** промт, инструменты, песочница, бюджеты. Поэтому под задачу сначала ищи пресет, а не собирай флаги руками — какие есть и для чего каждый, печатает `pia presets`.

Если что-то не работает — начни с `pia setup`: он покажет, найден ли бинарь pi, какие конфиги подхвачены и что чем перекрыто. Правила слияния слоёв и проектные надстройки — `docs/config.md`.
